# Récupération contrôlée d’un facteur plateforme perdu

Procédure opérateur, sans endpoint de contournement. Supprimer/réattribuer un rôle dans `private.platform_admins` ne supprime pas un facteur Supabase Auth. Référence : [API administrative deleteFactor](https://supabase.com/docs/reference/javascript/auth-admin-deletefactor).

1. Un administrateur actif ouvre un incident et fait vérifier l’identité par un canal indépendant de la session perdue. Un opérateur habilité confirme le projet dans `deploy/environments.json`, l’utilisateur Auth et les facteurs concernés. Consigner identifiants, motif, vérificateur et opérateur ; aucune clé, secret TOTP ou URL d’invitation dans le journal.
2. Révoquer l’accès plateforme et vérifier le refus serveur. Le rôle reste suspendu pendant toute la récupération. Si aucun administrateur actif ne subsiste, passer par le propriétaire du projet et son accès opérateur, après la même vérification indépendante.
3. Avec un client Auth administratif serveur, révoquer globalement les sessions (`auth.admin.signOut(accessToken, "global")`) si une session vérifiée est disponible. Contrôler la disparition des sessions dans `auth.sessions`. Sans jeton valide disponible, l’opérateur habilité révoque les sessions de cet utilisateur par les outils Auth du projet et vérifie leur suppression ; ne pas poursuivre si cette révocation ne peut être prouvée. Le registre suspendu continue de refuser les JWT éventuellement encore valides.
4. Inventorier les facteurs avec `auth.admin.mfa.listFactors({ userId })`, puis supprimer uniquement le facteur perdu avec `auth.admin.mfa.deleteFactor({ userId, id })`. Vérifier son absence. Ne pas réutiliser son secret et ne pas supprimer un facteur encore utilisable par supposition.
5. Le propriétaire se reconnecte, enrôle et vérifie un nouveau TOTP par Auth. Vérifier AAL2, identité et session active avant de réattribuer le rôle plateforme. Confirmer le refus des anciennes sessions et le succès avec le nouveau facteur ; fermer l’incident avec les preuves.

Preuve locale : `node tests/integration/platform-mfa.local.mjs node_modules/.cache/eventflow-security-b6`. La fixture utilise réellement Auth, MFA et le SMTP Mailpit local ; les invitations Auth ne passent pas par `MAIL_MODE=capture`. Elle vérifie la persistance du facteur après simple réattribution, la révocation globale, le refus de refresh, la suppression ciblée et un nouveau TOTP AAL2. Elle n’atteste pas une récupération distante ni la vérification humaine d’identité. Aucun test ne doit utiliser un compte client.
